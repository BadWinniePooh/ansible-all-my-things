# Contract: Playbook Invocation

**Feature**: `017-hcloud-web-frontend` | **Date**: 2026-08-24

The subprocess contract between the interface and `ansible-playbook`. This is the security
boundary of the feature: everything that keeps the two forbidden-to-persist secrets out of
storage, out of logs and out of the process list is expressed here.

## Invariants

These hold for every invocation, without exception.

1. **Secrets travel only in the child process environment.** They are never elements of the
   argument list. An argument list is readable through the process table by any local user
   and is echoed into the run view; a child's environment is neither.
2. **No secret is written to a file.** No temporary file, no memory-backed file, no
   password file. The vault password reaches Ansible through the repository's existing
   `scripts/echo-vault-password-environment-variable.sh`, which reads
   `ANSIBLE_VAULT_PASSWORD` from the environment.
3. **The command shown to the user is the command that runs.** The interface renders the
   argument list verbatim before starting. Because secrets are never arguments, the
   rendered command is safe to display in full.
4. **Output is never persisted.** It is streamed to the browser and held in a bounded
   in-memory buffer for the lifetime of the run view. Ansible can echo decrypted
   configuration values, so persisting output would defeat the encryption of the file those
   values came from.
5. **One run at a time.** The mutex is acquired before the subprocess starts and released
   when it terminates, including on cancellation and on failure.

## Environment

| Variable | Source | Present when |
|---|---|---|
| `ANSIBLE_VAULT_PASSWORD` | session secret store | always, for every action |
| `HCLOUD_TOKEN` | session secret store | always, for every action |
| `ANSIBLE_CONFIG` | baked into the image at `/ansible/ansible.cfg` | always |
| `PATH`, locale and similar | inherited from the container | always |

Nothing else from the interface process is forwarded. Both secrets are required for all
three actions: provisioning and destruction call the Hetzner API, and every action reads
the encrypted configuration.

## Working directory

`/ansible` — the baked repository checkout. `ansible.cfg` resolves `inventory` to
`./inventories`, which is the mounted volume, so the playbooks read the user's machine
records, host keys and configuration rather than anything baked into the image.

## Action: provision

```text
ansible-playbook /ansible/playbooks/create-vm.yml
  --private-key /ansible/inventories/.webui/ssh/id_ed25519
  --extra-vars provider=hcloud
  --extra-vars profile=<basic|desktop>
  --extra-vars hcloud_server_type=<server size>
  --extra-vars hcloud_server_location=<location>
  --extra-vars image=<operating system image>
```

Notes:

- The machine name is not supplied. `playbooks/tasks/create/hcloud.yml` claims the first
  free entry from the active name pool.
- The interface refuses before invoking when the pool is exhausted, because the automation
  claims a name before it calls the Hetzner API and would otherwise fail mid-run.
- On failure, the existing automation deletes the partially-created machine and fails with
  re-run instructions. The interface relays that rather than restating it.

## Action: configure

```text
ansible-playbook /ansible/playbooks/configure-profile.yml
  --private-key /ansible/inventories/.webui/ssh/id_ed25519
  --limit <machine name>
```

Notes:

- The profile is not passed. It follows from the machine's group membership in
  `hcloud_autogenerated.yml`, written when the machine was provisioned.
- `--limit` confines the run to the selected machine, so applying a profile to one machine
  never touches another.
- Re-running against an unchanged machine reports no changes (SC-008).

## Action: destroy

```text
ansible-playbook /ansible/playbooks/destroy-vm.yml
  --extra-vars provider=hcloud
  --extra-vars hostname=<machine name>
```

Notes:

- No private key is needed; destruction is an API call, not an SSH session.
- The interface requires the user to type the machine name before invoking.
- On success the machine's name becomes available in the pool again, because the pool's
  free set is computed against the machine records.

## Output handling

Standard output and standard error are merged and read line by line as the process runs.
Each line is appended to the bounded ring buffer and emitted to the Server-Sent Events
stream.

On termination the interface emits one terminal event carrying the outcome and the exit
code:

| Exit | Outcome |
|---|---|
| `0` | `succeeded` |
| non-zero | `failed`, with the tail of the output surfaced |
| terminated by cancel | `cancelled` |

A failure never reports a generic message. The underlying Ansible error is what the user
sees (Principle XII).

## Host key handling

Hetzner machines are internet-exposed, so host key verification stays on. The playbooks
already use `StrictHostKeyChecking=accept-new` against the project-scoped
`inventories/hcloud_known_hosts`, and remove the entry on teardown.

That file lives in the mounted volume, so host keys persist across restarts and upgrades.
A changed host key on a known address therefore still fails loudly rather than being
silently re-trusted, satisfying Principle XIV.

## What the interface must never do

- Pass `ANSIBLE_VAULT_PASSWORD` or `HCLOUD_TOKEN` as an `--extra-vars` value.
- Write either value to a file, including a memory-backed one.
- Echo either value into the run view, a log line, or an error message.
- Write run output to disk.
- Start a second run while one is active.
- Modify any file under `/ansible` outside the mounted volume.
