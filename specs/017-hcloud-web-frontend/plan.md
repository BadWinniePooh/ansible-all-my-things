# Implementation Plan: Hetzner Web Frontend for VM Provisioning

**Branch**: `017-hcloud-web-frontend` | **Date**: 2026-08-24 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/017-hcloud-web-frontend/spec.md`

**Tracking**: beads epic `ansible-all-my-things-bgvv`

## Summary

Package this repository as a self-contained container image that serves a
server-rendered web interface for the Hetzner Cloud lifecycle: provision, apply a
software profile, destroy. The interface drives the repository's existing playbooks as a
subprocess; it does not reimplement them.

The technical approach is deliberately conservative. Python is already the runtime that
Ansible itself runs on, so the interface is a Python web service with server-rendered
templates and no JavaScript build chain. The two secrets the spec forbids persisting — the
Hetzner API token and the vault password — are held in process memory and injected into
the subprocess environment, which is a path the repository already supports: `ansible.cfg`
routes `vault_password_file` through `scripts/echo-vault-password-environment-variable.sh`,
which reads `ANSIBLE_VAULT_PASSWORD` from the environment.

The image is independent of the `ansible-runner` image published by feature 016. That
independence is what makes minimal size achievable: the web image installs only the
collections and Python packages a Hetzner run actually touches, dropping the AWS and
Windows collections, the AWS SDK, and the Molecule test stack.

## Technical Context

**Language/Version**: Python 3.13 (container base and application runtime)

**Primary Dependencies**: `ansible-core` 2.21.1 (matching the pin in
`.docker/Dockerfile`), FastAPI, Uvicorn, Jinja2, httpx. Ansible collections:
`hetzner.hcloud`, `community.general`, `ansible.posix`. HTMX is vendored as a static asset
rather than loaded from a CDN, because the container must work without outbound access to
third-party hosts.

**Storage**: one container named volume mounted at `/ansible/inventories`. Holds the
Ansible-Vault-encrypted `group_vars/all/vault.yml`, the autogenerated inventory recording
live machines, the project-scoped `known_hosts`, and a hidden `.webui/` directory for the
name pool, presets, the SSH keypair and the seed marker.

**Testing**: `pytest` for the application; `container-structure-test` for the image, using
the existing checksum-verified binary pattern from `.github/workflows/docker-runner-publish.yml`.
No Molecule scenario, because this feature adds no Ansible role.

**Target Platform**: Linux container, `linux/amd64` and `linux/arm64`.

**Project Type**: server-rendered web service wrapping a command-line tool.

**Performance Goals**: first line of run output visible within 5 seconds of a run starting
(SC-011); interface actions that do not start a run respond in under 1 second.

**Constraints**: the Hetzner API token and the vault password are never written to
persistent storage, never logged, and never passed as `--extra-vars`; exactly one
automation run may be active at a time; the image carries nothing serving out-of-scope
providers, platforms or testing.

**Scale/Scope**: single operator per instance, one active run, roughly ten managed
machines (the default name pool size), six interface screens.

**Structure Decision**: the application lives in a single top-level `webui/` package
rather than a `backend/` plus `frontend/` split, because it is server-rendered and has no
separate client build. Its modules map one-to-one onto the entities in
[data-model.md](./data-model.md), which keeps each concern — secrets, vault, pool, presets,
keys, runs, seeding — independently testable. Container assets join the existing `.docker/`
directory, documentation follows the layout already established for the runner image, and
the compose files sit at the repository root where a new user will look for them.

## Modified existing files

Only one existing behaviour changes. `playbooks/tasks/create/hcloud.yml` currently loads
`playbooks/vars/hostname_pool_hcloud.yml` unconditionally. It gains a `stat` check that
prefers `inventories/.webui/hostname_pool_hcloud.yml` when that file exists, falling back
to the repository default otherwise.

Explicit selection is chosen over the alternative of letting `--extra-vars` win by
precedence. Both work, since extra vars outrank `include_vars`, but the explicit form is
self-documenting, is visible to anyone reading the task file, and works for command-line
users who never touch the web interface.

## Complexity Tracking

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| A Python web service (FastAPI, Uvicorn, Jinja2) — Technology Stack rule on additional runtime languages | The feature is a web interface; it cannot exist without a server process. Python is the language Ansible already runs on in this image, so no new language runtime is added — only libraries. | A Node or Go service would add a genuinely new runtime, a second toolchain and a build chain to an image the same feature requires to be minimal. A pure-static interface cannot run a subprocess, hold secrets out of storage, or stream output. Shell CGI would put secret handling into a language with no safe way to keep values out of the process list. |
| `pytest` as a test framework — not among the declared testing tools | The application is Python code with branching logic — secret lifecycle, key preservation on vault writes, pool validation, mutex behaviour — that must be tested without provisioning real machines. The declared tool, Molecule, tests Ansible roles and this feature adds none. | Testing only through `container-structure-test` would verify image composition but not one line of behaviour. Relying on manual end-to-end testing would make the "secrets never persisted" guarantee (SC-005) unverifiable, which is the one property that must never silently regress. |
| `requirements-web.txt` and `requirements-web.yml` restate subsets of the root requirements files — Principle XI | The user requirement that the web image be independent of the runner image, combined with the requirement that it be minimal, makes a separate reduced dependency declaration unavoidable. | Reusing the root files would ship the AWS SDK, the AWS and Windows collections and the Molecule stack into an image required to be minimal. Splitting the root files into shared fragments would reintroduce exactly the build coupling between the two images that was explicitly rejected. The duplication is a flat list with no logic, and the structure test asserts both the kept and the dropped components, so drift fails CI rather than shipping. |
| `.docker/Dockerfile.web` restates the builder-stage structure of `.docker/Dockerfile` — Principle XI | Same independence requirement. Two images that must not depend on each other need two build definitions. | A shared base stage would create the coupling the user rejected: the web image could not build without the runner image's context, and a change to one build would silently alter the other. The repeated portion is roughly fifteen lines of package installation with no branching. |
| The feature branch starts from `016-docker-runner-harness`, not `main` — Development Workflow step 2 | Feature 016 is twelve commits ahead of `main` and unmerged. Three of its changes are load-bearing here: the shape of `inventories/group_vars/all/vault-template.yml` that the configuration form is generated from, the packaging and publishing conventions this pipeline follows, and the issue-tracking database holding this feature's epic. | Branching from `main` would generate the configuration form from an outdated template, encoding wrong assumptions into the interface. Merging 016 first was offered and declined, as 016 is not yet review-ready. The deviation is recorded in the specification's Dependencies section so it survives independently of any tracker entry. |

## Phase 0 — Research

See [research.md](./research.md). It resolves the open technical questions: base image and
Python version, the reduced dependency set and the evidence behind each drop, how the
container tolerates a volume seeded by an older image, how secrets reach the subprocess
without touching disk or the process list, how run output is streamed, how the Hetzner SSH
key endpoints are used, and the two mechanisms that need empirical verification before they
are relied on.
